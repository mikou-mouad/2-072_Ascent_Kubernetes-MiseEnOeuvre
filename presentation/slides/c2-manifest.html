Chapitre 2 · Le concept

Anatomie d'un manifest

apiVersion: v1           # groupe/version de l'API
kind: Pod                # le type d'objet
metadata:                # son identité
  name: hello
  namespace: festipass
  labels:
    app: hello
spec:                    # l'état voulu : vous l'écrivez
  containers:
  - name: hello
    image: busybox:1.36
    command: ["sleep", "3600"]
status: {}               # l'état réel : Kubernetes l'écrit

Les apiVersion à connaître

v1 Pod, Service, ConfigMap, Secret, Namespace

apps/v1 Deployment, StatefulSet, DaemonSet

batch/v1 Job, CronJob

NE PAS ÉCRIRE DE MÉMOIRE

kubectl explain deployment.spec
kubectl api-resources
kubectl run hello --image=busybox:1.36 \
  --dry-run=client -o yaml > pod.yaml
kubectl apply -f pod.yaml

Les quatre champs de premier niveau sont toujours là. status est rempli par Kubernetes : on ne l'écrit jamais (kubectl get pod -o yaml le montre). kubectl explain est la documentation intégrée, champ par champ (--recursive pour tout voir). --dry-run=client -o yaml génère un squelette correct qu'on complète : c'est la méthode recommandée, y compris à l'examen CKA.
