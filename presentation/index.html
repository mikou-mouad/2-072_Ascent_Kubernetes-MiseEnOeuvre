Gérer les nœuds

kubectl get nodes -o wide
kubectl label node worker-1 disque=ssd
kubectl get nodes -L disque

kubectl cordon worker-2       # plus de nouveaux pods
kubectl drain worker-2 --ignore-daemonsets \
  --delete-emptydir-data     # vide le nœud
kubectl uncordon worker-2     # retour en service
kubectl delete node worker-2  # retirer (après drain)
sudo kubeadm reset           # sur worker-2, puis join

kubectl describe node control-plane | grep Taints
  node-role.kubernetes.io/control-plane:NoSchedule
kubectl describe node worker-1   # Capacity, Allocatable

Label

Une étiquette sur le nœud, pour choisir où placer un pod.

cordon · drain · uncordon

La maintenance : fermer, vider, rouvrir. Ou retirer le nœud, puis le réintégrer.

Taint

Repousse les pods : le control plane refuse les pods ordinaires.

Capacity · Allocatable

Ce que le nœud possède, ce qu'il laisse aux pods.

drain expulse les pods proprement : ceux d'un Deployment sont recréés ailleurs. Garder cette commande en tête : c'est un drain qui déclenchera l'incident du chapitre 6. Au TP, on retire worker-2 du cluster (drain, delete node, kubeadm reset sur le worker), puis on le réintègre avec la commande donnée par kubeadm token create --print-join-command. On arrête aussi le scheduler (kube-scheduler.yaml sorti de /etc/kubernetes/manifests) : les nouveaux pods restent Pending. La taint du control plane explique pourquoi les pods de FestiPass n'y atterrissent jamais ; on la retirera au TP 08 pour gagner de la capacité. Allocatable = Capacity moins ce que le système et le kubelet se réservent.

Anatomie d'un manifest

  name: hello
  namespace: festipass

Les apiVersion à connaître

v1 Pod, Service, ConfigMap, Secret, Namespace

apps/v1 Deployment, StatefulSet, DaemonSet

batch/v1 Job, CronJob

NE PAS ÉCRIRE DE MÉMOIRE

kubectl explain deployment.spec
kubectl api-resources
kubectl run hello --image=busybox:1.36 \
  --dry-run=client -o yaml > pod.yaml
kubectl apply -f pod.yaml

Les quatre champs de premier niveau sont toujours là. status est rempli par Kubernetes : on ne l'écrit jamais (kubectl get pod -o yaml le montre). kubectl explain est la documentation intégrée, champ par champ (--recursive pour tout voir). --dry-run=client -o yaml génère un squelette correct qu'on complète : c'est la méthode recommandée, y compris à l'examen CKA.

Service ClusterIP

Chapitre 8 · Le concept

HPA : le nombre de pods suit la charge

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: back, namespace: festipass}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: back}
  minReplicas: 2
  maxReplicas: 8
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: {type: Utilization, averageUtilization: 60}
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120   # descendre lentement

desiredReplicas =
ceil(current × usage / cible)

2 pods à 180 % de leurs requests :
ceil(2 × 180 / 60) = 6 pods

60 % de quoi ?

Des requests CPU du pod : 60 % de 250m = 150m.

Prérequis

metrics-server (TP 04) et des requests CPU (TP 05).

Le HPA est une boucle de plus : toutes les 15 secondes, il lit les métriques et ajuste replicas du Deployment. Sans requests, le pourcentage n'a pas de sens : le HPA affiche . La montée est rapide, la descente amortie par stabilizationWindowSeconds (300 s par défaut) pour éviter le yo-yo. Ne plus fixer replicas dans le manifest du Deployment : un apply écraserait la valeur choisie par le HPA.

RBAC : qui peut faire quoi

Authentification · « Qui es-tu ? »

Un certificat client (kubeconfig) ou un token de ServiceAccount. Kubernetes ne stocke pas d'utilisateurs.
